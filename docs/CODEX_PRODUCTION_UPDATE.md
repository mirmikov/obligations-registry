# Безопасное обновление production через Codex

Production-сервер хранит рабочую PostgreSQL-базу в Docker volume. Код синхронизируется через GitHub, а база, `.env` и резервные копии не входят в Git и не заменяются при обновлении.

## Один раз: сохранить исправления, сделанные прямо на сервере

Сейчас на рабочем компьютере есть исправления, которых ещё нет в GitHub: форма входа, импорт дат и сумм, синхронизация контрагентов со справочником и права редакторов на добавление значений. До первого автоматического обновления их обязательно нужно перенести в GitHub.

Запустите Codex в `/home/mirmikov/obligations-registry` и дайте ему этот текст:

> Проверь production-репозиторий и ничего не разворачивай. Покажи `git status --short`, текущий коммит и полный diff относительно `origin/main`. Сохрани все рабочие server-only исправления в новой ветке `mirmikov/production-hotfix-sync`, не добавляя `.env`, базу, дампы и секреты. Запусти backend-тесты и frontend-сборку, отправь ветку в GitHub и создай PR в main. Не выполняй `docker compose down`, не пересоздавай PostgreSQL и не импортируй Excel. После PR остановись и дай отчёт по файлам и проверкам.

После проверки PR объедините его с `main`. Только после этого разрешается автоматическое production-обновление.

## Один раз: включить безопасный production-режим

В `/home/mirmikov/obligations-registry/.env` добавьте строку:

```dotenv
RUN_DATABASE_MIGRATIONS=false
```

Проверьте, что `.env` имеет права `600`. Не копируйте `.env.example` поверх рабочего `.env`: там находятся production-пароли и секреты.

## Обычное обновление после слияния изменений в main

Запустите Codex на рабочем компьютере в каталоге проекта и дайте ему этот текст:

> Обнови production-платформу из `origin/main`, не изменяя рабочую базу. Сначала прочитай `AGENTS.md`, проверь чистоту Git, текущий коммит, наличие `.env` и `RUN_DATABASE_MIGRATIONS=false`. Затем выполни `./ops/production/update-from-github.sh main`. Не запускай `docker compose down`, не используй флаг `-v`, не импортируй Excel и не изменяй PostgreSQL вручную. После обновления сообщи старый и новый commit, путь к проверенному backup, состояние контейнеров, health-check и контрольные показатели базы до/после.

Скрипт автоматически:

1. остановится, если на сервере остались незакоммиченные исправления;
2. получит только fast-forward обновление из GitHub;
3. создаст и проверит дамп в `/home/mirmikov/backups/obligations-registry`;
4. соберёт новые образы без остановки текущих контейнеров;
5. пересоздаст только `backend` и `frontend` с `--no-deps`;
6. проверит, что контейнер и volume PostgreSQL не менялись;
7. сравнит количество обязательств, общую сумму, пользователей, справочники и сообщения до и после;
8. проверит `/api/health` и покажет состояние контейнеров.

## Что делать, если обновление остановилось

- `репозиторий содержит локальные изменения` — ничего не удалять; вынести изменения в отдельную ветку и PR.
- `RUN_DATABASE_MIGRATIONS=false` отсутствует — добавить только эту строку в существующий `.env`.
- изменились контрольные показатели базы — не повторять обновление и не восстанавливать дамп автоматически; сохранить вывод и попросить Codex провести read-only диагностику.
- нужна новая колонка или таблица — это отдельная миграция базы. Сначала backup, затем проверенный SQL-план и явное подтверждение пользователя; обычный скрипт code-only deploy для этого не используется.

Главное правило: GitHub является источником кода, PostgreSQL volume — источником рабочих данных. Они обновляются раздельно.
